# 新リポジトリのフォルダ・素材管理方針

| 保存先 | 役割 | 入れてはいけないもの |
|---|---|---|
| `src/` | 採用中のゲームプログラム | 使い捨て試験コード・配信物 |
| `data/` | マップ・イベント・会話の構造化データ | 名前違いのコピー |
| `assets/` | 採用済みゲーム素材 | 未承認・比較・中間生成物 |
| `source-assets/` | 再編集が必要な採用素材の元データ | 完成画像の複製 |
| `.agents/skills/` | 再利用可能な手順の唯一の正本 | 重複・類似スキル |
| `docs/` | 現行設計と意思決定 | 旧版設計を現行と誤認させる資料 |
| `tools/` | 共通加工・検査スクリプト | 試作用の一時スクリプト |
| `tests/` | 自動検査 | テストの生成結果 |
| `work/` | 一時作業（Git管理外） | 採用素材の唯一の正本 |

空フォルダを `.gitkeep` で大量に作らず、実際に使う際に新設する。`old/` に旧実装を丸ごと保管せず、Git履歴または元リポジトリを利用する。

## 公開検証用プレビューの限定例外

- 個別に検証用途を限定した例外は **`previews/cave-prototype/index.html`**（洞窟の接続検査）および **`previews/field-overlook/index.html`**（花霞野の高台を既存32pxマップチップ・水面アニメ・歩行操作で再現するための構成検査）の各単独HTMLである。花霞野の候補はユーザーレビューまでの一時的な試作であり、本編反映時には継続の必要性を判断して撤去する。
- **`previews/field-exploration/index.html`** は現行地形 `main` を読み込み、PR #2 (`improve/field-early-exploration`) の地形差分のみを実行時に適用して歩行確認する専用ページ。ユーザーからGitHub Pages公開の明示指示を受けた限定例外であり、レビュー終了後に撤去する。ゲーム本編のデータや採用素材は変更しない。
- **`previews/shoreline-study/index.html` は海と砂浜の16形状接続・寄せ引き波の合格済み試作**。海岸より内陸側は最小9セルの砂浜で、原寸岩3点を配置。追加の限定検証では、**戦闘が5回完了するごとにランダムな1〜3個の貝殻を補充する**。乱数で位置を変えず、砂浜の常設採集ポイントへ補充し、画面を開くだけでは増やさない。貝殻の浜辺在庫は最大12個。戦闘数は `src/game/battle/rules.mjs` の勝利・敗北・逃走すべてを数える `completedBattles` を参照する。検証ページ固有の採集処理は `data/maps/shoreline-study/shells.mjs` に残し、貝殻3種の買取価格・補充回数と20pxのドット絵は `src/game/items/shells.mjs` / `src/game/items/shell-art.mjs` を正本として共有する。**検証ページの所持数と買取額は `SHELL_SAVE_KEY` のみへ記録**し、正式なプレイヤー所持金とは混ぜない。一方、本編「海の入り江」は `data/maps/sea-cove/shells.mjs` の固定採集地点に戦闘5回完了ごと1〜3個補充し、`src/game/battle/rules.mjs` のプレイヤーセーブへ貝殻所持数・未回収地点を記録する。現行鬼灯村の**茶店**でのみ売却でき、売却時に本編所持金へ加算する。波の規則は `src/game/terrain/surf.mjs` に一本化し、合格済み検証ページと本編入り江で共有する。本編 `COVE_SAND_DEPTH` は10〜14セルの幅を行ごとに明記し、南側を細い草地の通路で繋がず砂浜のまま出口に接続する。東側の海岸は既存16形状マスクからワールド座標で距離を求め、8コマの32px波タイルアトラスを起動時に構築する。砂浜から内陸の草地・濃い森へは同じ16形状マスクで接続し、人工的な正方形パッチを作らない。矩形の濃い森クラスターは角の形を欠いて自然な輪郭にする。`assets/field/objects/wildflowers.png` は4×4のチップ集なので**全16枚をひとつの巨大オブジェクトとして描くことは禁止**し、配置データの指定した1枚の32pxチップのみを原寸で描画する。描画時に全画面の波オーバーレイは重ねない。カメラ倍率・ヒヅキ原寸・潮平・貝殻の採集位置を無断で変更しない。
- **`previews/sea-cove-review/index.html` はユーザーが今回の本編未完成マップの公開検査を許可した、GitHub Pages限定の一時レビューHTML。** `main` の `src/game/cove/walk.mjs` と `render.mjs`、既存素材を読み込み、波アニメ・描画と歩行を実際に確認する。デモ用の独自地形データ・レンダラーを作成しない。プレビューモードは保存データ・物語段階・退出時の本編ルートを変更しない。GitHub Pages以外の外部CDNには公開しない。完了後は必要に応じてHTMLとその個別許可を撤去し、正式本編は維持する。
- `previews/` ディレクトリ全体を許可したわけではない。追加HTML、画像、バージョン違い、他のプレビューを保存するには、目的・期限・重複を確認し別途承認と検査を要する。
- これらの検査用HTMLの追加はゲーム本編への導入や、新しい画像素材の採用承認を意味しない。`assets/` の採用台帳運用は従来どおり保持する。
- GitHub Pagesの公開設定・デプロイ状況・Safari実機動作は、リポジトリの`npm test`とは別に確認する。

## 正式識別子の命名基準
- アセットID・保存パス・ランタイム用の設定値は、**用途、向き、サイズ、フォーマット**など仕様上の区別に必要な属性で一意に命名する。例: `hizuki-walk-4dir-80x112`（4方向・1コマ80×112px）。
- AIが作った仮の愛称や制作日、`new` / `old` / `final` といった状態説明を、そのまま正式な識別子にしない。
- 移行元で使われた命名は履歴追跡のため `origin.path` / `sourceOriginalPath` のみに保管し、現行ID・アセットパス・描画切替の値へ伝播させない。
- 正式名を変える場合は既存ファイルの**移動**として扱い、台帳・設定JSON・全参照・QAを同一コミットで更新する。新旧の完成画像を並存させない。アセットのGit Blob SHAが同じであることを検証する。
- ユーザー未承認の名称を「採用版」や既定値の根拠にしない。表示する際には意味が分かる名称で説明する。

## 採用手順
1. `assets/manifest.json` と既存のファイルを検索し、重複を確認。
2. 再利用・画像加工で対応できるか検討。必要なら `work/` で試作。
3. ユーザーの承認と品質検査が済むまで `assets/` に入れない。
4. 採用されたファイルを用途別の安定パスへ**1つだけ**保存し、台帳へID・パス・型・採用状態を記入。
5. 再編集が必要な原本だけ `source-assets/` に登録し、台帳の `sourcePath` とリンク。
6. `npm test` とゲーム内の見た目・動作を別々に検査してから報告。改訂時は同じ正本パスを更新し、旧版はGit履歴へ残す。

## 素材台帳の記入例
以下は**例示**であり、現時点で採用されている素材ではありません。

```json
{
  "schemaVersion": 1,
  "assets": [
    {
      "id": "hizuki-idle",
      "type": "character",
      "path": "assets/characters/hizuki/idle.png",
      "status": "approved",
      "sourcePath": "source-assets/characters/hizuki/idle-source.png"
    }
  ]
}
```

`sourcePath` は原本が必要で**実際に保存する場合だけ**付ける。任意に `origin`、`license`、`approvalNote` 等の追跡情報を追加できる。`path` は常にリポジトリ相対パス。

## 正式デザイン原画
正式な衣装・四面図などの**デザイン原本**はゲーム用の画像とは別に `source-assets/` に置き、`assets/manifest.json` の `designReferences` に原本パス・SHA-256・用途を登録する。派生画像を作っていないときはゲーム用画像の `sourcePath` に誤って紐づけない。原画像は無加工で保持し、Git blobと実バイトで照合する。

## 自動検査と限界
`tools/check-repository.mjs` は、怪しい旧版/一時保管先、未登録素材、素材IDとパスの重複、ファイル不在、採用素材・原本の完全一致重複を検出する。**見た目の近似重複・画質・ライセンス・ゲーム動作・iPhone Safari**については別途検査する。

GitHub Actionsはpush後に検査するため、直接mainへコミットした内容を事前にブロックしない。
